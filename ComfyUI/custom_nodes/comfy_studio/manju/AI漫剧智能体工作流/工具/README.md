## 为什么需要这个工具

本项目的权威内容分**三层**，改上层不改下层会导致一个隐蔽的 bug：

```
① 事实来源层   规格原文 · 各模块 00-主控智能体.md
② 规则/引擎层  引擎/*.md · 模块 README.md
③ 实体层       ⚠️ 模板/* · 可部署的合并版/总集 · 项目骨架/ 下 _README
```

**问题**：你打开主控看，内容是对的——就以为改完了。但**用户实操时复制的正是第 ③ 层**，拿到的是被取代的旧格式。

**真实案例（2026-09-23）**：把 06 合规主控从「八类风险/六法优化」升级为「十类/八法」并加了未决项联动，也更新了 README 与引擎文件——**但忘了同名模板**。结果用户按模板做合规检查时，拿到的仍是八类/六法。同类问题一次查出 **8 处**。

其中一处尤其严重：`03-分镜导演/README.md` 写了 ID 规则，但**真正粘贴进 GPTs 的两个主工作流文件里一条都没有**——部署出去的 agent 完全不知道有 ID 注册表，整条 ID 机制在 01 环节形同虚设。

**所以：改完请跑一次本工具。**

## 用法

```bash
cd AI漫剧智能体工作流
python 工具/校验.py            # 全量检查
python 工具/校验.py -v         # 额外显示通过的项
python 工具/校验.py --only 机制  # 只跑某一类（引用/机制/禁用/口径/交付包）
python 工具/校验.py --sizes    # 打印可部署文件体积，供部署指南刷表
```

**退出码**：`0` = 全部通过；`1` = 存在失败项（可接入 CI 或提交前钩子）

**依赖**：Python 3.8+，纯标准库，无需安装任何包。

## 十二类检查

| # | 检查 | 抓什么 | 触发场景 |
|---|---|---|---|
| 1 | **引用完整性** | 路径式引用指向不存在的文件；**旧模块编号**残留（`04/xxx`） | 文件改名/移动、**模块重编号**后忘了更新引用 |
| 2 | **机制覆盖** | 某机制的关键词没在该出现的文件里出现 | **改主控忘了同步模板** |
| 3 | **禁用前缀** | 已废弃 ID 前缀残留（`SHOT_`/`SCN_`/`SHO_`/`MUS_EP`） | 命名规范改了但全库没 grep 干净 |
| 4 | **口径一致** | 旧口径词残留（如 06 模块仍写"八类""六法"） | 升级数字口径后漏改部分文件 |
| 5 | **交付包字段** | 交付包缺 ID 或未决项字段 | 新增跨模块机制后没推广到所有模块 |
| 6 | **素材完整性** | 规格原文 / 源 skill / 模板被误删 | **误删参考 md**（用户明确要求保留） |
| 7 | **文本完整性** | 全角括号不配对 + 损坏指纹 | **字符级替换事故**（见下） |
| 8 | **数字声明** | 文档里的体积/行数/个数/总量过时 | **内容更新后忘了刷新文档里的数字**（见下） |
| 9 | **目录树一致性** | README 的树里有不存在的条目 | **模块重编号/文件挪位后忘了改树**（见下） |
| 10 | **结构引用一致性** | `【0N 模块名】` 编号错、`文件.md §X` 章节不存在 | **重编号后正文编号没改 / 章节重排后 § 引用失效**（见下） |
| 11 | **共享表头一致性** | 同一张表在多处的表头不相同 | **改了工作流没改可部署的合并版**（见下） |
| 12 | **档位声明一致性** | frontmatter 声明的档位与**本文档章节标题**不符 | **改了章节档位忘改 frontmatter**（"改一半"，见下） |

### 检查 12 的由来：同一个文件自己跟自己矛盾

**2026-09-23**，就在修 v41 收尾时顺手核对档位，发现 `03-分镜导演/视觉分镜引擎.md` 的
**frontmatter `description`** 写着「6 景别/7 角度/6 构图/13 运动/7 光影系统」，
而**同文件** §4.2–§4.6 的标题实际是：

| 系统 | §4.x 标题实际 | frontmatter 却写 |
|---|---|---|
| 景别 | 镜头景别系统（**7 级**） | 6 ❌ |
| 角度 | 摄影机角度系统（**8 种**） | 7 ❌ |
| 构图 | 构图系统（**9 种**） | 6 ❌ |
| 运动 | 摄影机运动（13 种） | 13 ✅ |
| 光影 | 光影系统（**8 种** + 氛围词） | 7 ❌ |

而 frontmatter 的 `description` **正是用户在平台上看到的「技能描述」**。

**这不是第一次**：v41 补强时景别/角度的声明**改过了**，构图/光影的**漏改了**——
**「改一半」是本项目的高发形态**（同 §五·4「改权威层必须同步实体层」）。

**设计优势：纯文件内比对** —— 不涉及跨文件歧义，**天然低误报**。
（对比：叙事分镜引擎合法地写「景别七级 / 角度五式 / 构图六法」，那是**另一个文件**，互不影响。）

**两条口径缺一即误报**：

| # | 口径 | 为什么 |
|---|---|---|
| ① | 只在 **YAML frontmatter 的 `description:`** 里找「N 系统名」声明 | 正文里可能出现在别的语境 |
| ② | 只认**编号子章节标题**（`### 4.2 …（N 级/种）`）为「实际档位」 | `### 2.7 光影` 这类没带「（N 种）」的标题不算，否则误判 |

> **顺带修掉的 3 处**：`视觉分镜引擎.md` frontmatter、`03-分镜导演/README.md` 的引擎对比表
> （左列把**我方旧值** 6 景别/7 角度错当成叙事引擎的档位，实为 **7 景别/5 角度/6 构图法**）、
> `03-分镜导演/_规格原文/README.md` 的资产清单（`6 构图`→`9 构图`、`7 光影`→`8 光影`）。

### 检查 10 的由来：三类「手写结构引用」曾是盲区

检查 9（目录树）上线后**紧接着自问「还有哪些同类手写结构声明没人管」**，又找出两类：

| 引用形态 | 失效后果 | 为什么检查 1 抓不到 |
|---|---|---|
| `【0N 模块名】` | 把人指到**错误的模块** | 是纯文字，不是反引号路径 |
| `文件.md §X` | 读者翻到不存在的章节 | 同上 |

**先审计再建检查**（本项目纪律）——审计结果：`【0N】` 25 处引用全对；`§` 引用 **70 处全部命中**。内容当前是对的，但 v39 刚做过模块重编号（最高风险操作），故仍固化。

**⚠️ 收窄规则 6 条**（全部实测踩出来，首版一次误报 16 处）：

| # | 规则 | 踩坑实例 |
|---|---|---|
| a | **`§` 必须紧跟文件名（≤2 字符）** | `` `PROJECT-PIPELINE.md` …（§25 §26 §41）`` 里的 §25 指**规格原文**的节号，不是该文件的第 25 章 |
| b | **取 `§` 前面「最近」的 .md** | `` `A.md` + `B.md` §1.5 `` 的 § 指 B 不指 A |
| c | **非模块引用要排除** | `【01 声音设计引擎】` 是模块**内部**引擎文件序号，不是顶层模块 |
| d | **两种标题风格都要认** | 项目里 `## 五、xxx` 与 `### 5.5 xxx` 并存；且**必须先认多级点号编号**，否则 `### 3.5` 会被「章号+分隔符」规则抢走 → 子节表全空 |
| e | **子节号要还原成全号** | `§4.2` 解析出 sec='4'/sub='2' → 全号 `4.2`；`§五·5.5` 的 sub 本身已是全号 |
| f | **兜底解析只用全库唯一的 basename** | `README.md` 全库 10 个，强行解析必然指错（同检查 8 的教训） |

**首次上线就跑出 3 处真实失效** —— 而且是靠**顺带修好检查 1 的一个缺陷**才暴露的：

> 检查 1 原有一条「同名文件在别处存在 → 降级为提示，不算失败」的放宽规则。
> 它把 v39 残留的旧编号引用（`` `04/` `` 打头 + 规格原文路径）**一直隐藏着**——
> 只因「别处存在某个 `README.md`」。
> 现改为**外科式**：只对「首段是裸模块号 `0N/`」这一类严格判定（其余保持原放宽规则），
> 并附 **v38→v39 旧编号映射表**给出精确修复建议。

### 检查 11 的由来：表头靠人工保持一致

审计发现「九列标准分镜表」的表头在**三处**重复定义：

| 文件 | 说明 |
|---|---|
| `03-分镜导演/主工作流/storyboard-director-pro.md` | 工作流本体 |
| `03-分镜导演/分镜导演-完整合并版.md` | **部署首选**（用户就是复制它的） |
| `示例演示/01-全流程走通.md` | 实跑示例 |

检查 2「机制覆盖」只能验证**关键词在不在**，无法验证**表头是否逐字相同**——故单列此项。规则以声明式表格写在 `校验.py` 顶部 `SHARED_TABLE_HEADERS`，新增一张共享表只需加一条。

### 检查 9 的由来：README 的目录树是「人类可读的结构声明」

**2026-09-23 用户报障**：「根 README 这里的目录树不对啊」。核查出三类失效，而**前 8 类检查全都发现不了**——

因为目录树不是路径式引用（检查 1 只抓反引号包起来的 `` `路径` ``），而是**散文式的结构描述**：

| 失效类型 | 具体表现 |
|---|---|
| **顺序错乱** | 模块重编号为 `01→06` 后，树里仍是旧顺序 `03→02→04→05→01→06` |
| **漏列内容** | 少了 `02-服化道/_archive/`、`99-源仓库索引/规格覆盖率审计.md` |
| **数字过时** | Suno 引擎写 29KB（实为 30.6KB）、合并版写 31KB（实为 31.9KB） |

> **为什么容易漏**：改目录/改名时，路径式引用有检查 1 兜着，而**树是手写的、无人检查**。

**⚠️ 必须收窄范围（首版未收窄 → 一次误报 45 项）**：

「树形结构」在本项目里被用于**四种不同用途**，只有第一种该被检查：

| 用途 | 例 | 是否检查 |
|---|---|---|
| **仓库目录树** | 根 README / 各模块 README 里的结构说明 | ✅ **检查** |
| 概念结构图 | `镜头技法扩充库.md` 里的 `├── §4.2 景别`、`├── C 焦点与光学` | ❌ 跳过（非文件） |
| 骨架示意 | `项目骨架/README.md` 里的 `PROJECT_STATE`/`CHARACTER_001`（**待创建**，本就不存在） | ❌ 跳过 |
| 外部目录树 | `资料素材全清单.md` 里的 `data/资料/` 结构 | ❌ 跳过 |

故检查 9 **只作用于此白名单**：根 `README.md` 与各模块 `0X-*/README.md`；并跳过含 `→` 的接线图块、纯 ASCII 框线条目、含 `<`/`…` 的占位符。

> **自测**：向根 README 树注入「不存在的引擎.md」+「不存在的目录/」→ **两条均被定位**；还原后全通过、无残留。

### 检查 8 的由来：四类「数字声明」失效（项目高发点）

**数字声明是本项目最容易过时的一类内容**，历史上已踩过至少 4 次：

| # | 事故 | 表现 |
|---|---|---|
| 1 | 合并版去重 | 77.3KB → 30KB 后，多处文档仍写 77.3 |
| 2 | 部署指南体积表 | 8 项数据**全部**过时（主控陆续增长） |
| 3 | **行数误计** | PowerShell `(Get-Content).Count` 数出 1824，Python 实数 2344；**只改了索引、漏改正文 2 处** |
| 4 | 根 README | 体积行写「102 / 753 KB」，实际 123 / 1230 |

**检查 8 覆盖四类声明**：体积（`` `x.md` ｜ 31.4 KB ``）· 行数（`817 行`）· 个数（`引擎 (8 个)`）· 总量（`<N> 个文件`）。

> ⚠️ 上行的「总量」示例**故意写成占位符 `<N>`** —— 写成真实数字会被检查 8 自己当成
> 「现状声明」比对，随文件数变化而失效（本项目已踩过 3 次）。

> **体积按 LF 归一化后度量**（`file_kb()`）——**不能用 `os.path.getsize`**。
> `.gitattributes` 声明 `* text=auto eol=lf`，但工作区里大量文件实际是 **CRLF**，两个来源：
> ① 源仓库抓取时原样保留；② **工具写入时被 Python 默认换行翻译悄悄改掉**
> （读 `\r\n`→`\n`，写 `\n`→`os.linesep`=`\r\n`；而 `git diff` 因 `.gitattributes`
> 归一化**看不见**这个改动——典型静默漂移）。
> CRLF 版本比 LF 大「行数」个字节：**700 行 = +0.68 KB**，足以让体积声明被**误判为过时**
> （2026-09-23 自测时就踩到：一次写入让 `分镜导演-完整合并版.md` 从 31.9KB 变成 32.6KB）。
>
> ⚠️ **推论：自测脚本读写文件必须带 `newline=""`**，否则「还原」会静默改变行尾，
> 表现为「明明还原了却仍报失败」。

**⚠️ 三条豁免（缺一就会误报，都是实测踩出来的）**：

| 豁免 | 为什么 | 不豁免的后果 |
|---|---|---|
| **只查全项目唯一的文件名** | `00-主控智能体.md` 在 5 个模块都存在，文档里写「24.3 KB」时无法判断指哪个 | 首版误报 7 处 |
| **跳过含 `→` 的行** | 那是提炼过程描述（「2344 行 → 481 行」），不是现状声明 | 误报全部提炼记录 |
| **跳过同行有 ≥2 个同类数字的** | 那是「前后对比」写法（版本说明「实跑时 724 行…现为 777 行」、错误日志「1824 行 \| 2344 行」） | 首版误报 5 处 |

> **自测**：向 `01-资产库出图引擎.md` 注入「`\| 12.3 KB`」（实际 37.4 KB）→ 准确定位到 `:732`；还原后全通过、无残留。

### 检查 7 的由来：一次真实的文件损坏事故（2026-09-23）

用 PowerShell 批量替换中文文本时踩了一个隐蔽的坑：

```powershell
# 想替换两个片段，写成嵌套数组
$map = @{ "f.md" = @(@("视觉分镜引擎.md ⭐【视觉分镜】…", "视觉分镜引擎.md ⭐【视觉分镜】…")) }
foreach ($pair in $map["f.md"]) { $c.Replace($pair[0], $pair[1]) }
```

`@(@("a","b"))` 这种**单元素数组会被 PowerShell 展开**，`foreach` 拿到的是**字符串**而不是数组。
于是 `$pair[0]` 取到的是**首字符**，`.Replace()` 退化成**字符级替换**：

| 本意 | 实际执行 | 后果 |
|---|---|---|
| 替换「视觉分镜引擎.md …」 | `Replace('视','觉')` | **全文所有「视」→「觉」**："视觉"→"觉觉"、"视频"→"觉频"、"三视图"→"三觉图" |
| 替换「676 行 / 27.4 KB」 | `Replace('6','7')` 再 `Replace('7','3')` | **全文所有 6 和 7 → 3**，数字全毁 |

**3 个文件被静默损坏，而当时 6 类检查全部通过。**

**检查 7 的设计**：

| 手段 | 说明 |
|---|---|
| **全角括号配平** | 中文文档里 `（`/`）` 逐行配平；字符级替换极易打破（实测一次事故 25 行不配对）。**最可靠的信号** |
| **损坏指纹** | 正常中文不存在的组合：`觉觉` / `觉频` / `三觉图` / `13:9`（应为 16:9） |
| **容忍阈值** | 文件级失衡 ≥2 **且**不配对行 ≥3 才报——避免单行笑脸 `:)` 之类噪声（首版就是被这个假阳性绊了一下） |

> ⚠️ **结论（已写入根 README 质量守则）**：
> **不要用 PowerShell / sed 做中文内容的批量替换**——数组展开、编码、换行符都可能静默损坏文件。
> 改用编辑工具（走 Python），或替换后立刻跑 `python 工具/校验.py`。

### 检查 6 的规则（素材不得误删）

用户明确要求：**参考的 md 很有用，尽量保留、不要删除**。故本检查守护两类资产：

| 类型 | 规则 | 位置 |
|---|---|---|
| **必须存在的具体文件** | 逐项核对存在性 | 见 `校验.py` 的 `REQUIRED_FILES`（规格原文归档、ID/未决项模板、源映射清单、工具自身） |
| **目录最小文件数** | 少于阈值即报警 | 见 `REQUIRED_DIR_MIN`（分镜源 skill ≥10、服化道源 skill ≥22、引擎 ≥8、规格原文 ≥3…） |

> 实现注意：本检查**直接查文件系统**（不依赖 `walk_files` 的扩展名过滤），否则 `.py` 等非 md/yaml 文件会被误判为缺失——这个 bug 在本检查首次运行时就被自己抓到了。

### 检查 1 的豁免规则（避免误报）

以下引用**不算断链**，已内置豁免：

| 类型 | 例 | 为什么不算 |
|---|---|---|
| 项目内部路径 | `00_PROJECT/ID-REGISTRY.md` | 项目中才会有，库内不存在属正常 |
| 源仓库待抓清单 | `角色/四视图大师.md` | INDEX 的用途就是列待抓项 |
| 源 skill 内嵌 references | `references/core-methodology.md` | 是源 skill 自带的参考库章节，不是独立文件 |
| glob 通配 | `引擎/*.md` | 非具体文件引用 |

## 如何新增检查

规则以**声明式表格**写在 `校验.py` 顶部，加检查只需加一条规则，**无需改逻辑**：

### 新增「机制覆盖」规则

```python
MECHANISM_RULES = [
    ...
    {
        "name": "你的机制名",
        "keyword": "必须出现的关键词",
        "must_in": [
            "该机制应出现的每个文件路径",
        ],
    },
]
```

### 新增「禁用前缀」

```python
FORBIDDEN_RULES = [
    ...
    {
        "name": "说明",
        "pattern": r"错误前缀_",
        "should_be": "正确前缀_",
        "exempt_files": ["归档目录/*"],        # 豁免文件（glob）
        "exempt_line": r"不是|已废弃|勿部署",   # 豁免「说明性文字」行
    },
]
```

> **豁免项设计说明**：很多"错误前缀"出现在**警示文本**里（如"分镜是 `SHT_` 不是 `SHOT_`"）。`exempt_line` 就是为了区分「用错」与「提醒不要用错」——没有它会产生大量假阳性，工具就会被人忽略。

## 已发现的「文档数字漂移」问题（附 `--sizes` 的由来）

体积/行数这类**硬编码在文档里的数字**极易过期。本项目实测：

| 位置 | 曾写 | 实际 | 原因 |
|---|---|---|---|
| `快速部署指南.md` | 合并版 77.3 KB | 31.4 KB | 上轮去重后忘了改 |
| 各处 | 调音大师班规格 1824 行 | 2344 行 | **PowerShell `(Get-Content).Count` 计数不准**，需用 Python `count("\n")` 核对 |
| 各处 | Suno 规格 2482 行 | 3038 行 | 同上 |
| `04/README` | 02 引擎约 560 行 / 21.4 KB | 724 行 / 28.8 KB | 估算未实测 |
| `01/_规格原文/README` | 视觉分镜引擎 24.8 KB | 25.5 KB | **文本模式读取 + 编码计数会偏小**（见下） |

### ⚠️ 第二种测量陷阱：换行符

本项目实测：`write_to_file` 在本系统产生 **CRLF** 文件，而用户提供的规格原文是 **LF**。

| 测量方式 | 结果 | 是否正确 |
|---|---|---|
| `os.path.getsize(p)` | 25.5 KB | ✅ 磁盘真实体积 |
| `open(p).read()` → `.encode('utf-8')` 后取长度 | 24.8 KB | ❌ **偏小**（文本模式把 `\r\n` 归一为 `\n`，每行少 1 字节） |

**结论**：
1. **体积一律用 `os.path.getsize`（即 `--sizes` 的口径）**
2. **行数用 `count("\n") + 1`**
3. 混用两种口径会导致"同一文件两个体积"——本项目已踩过一次

## 三、融入新规格的标准流程（已实践 2 次）

用户提供一份新规格（通常 2000-3000 行 / 70-80 节）时，按以下顺序做：

```
① 原文归档
   复制到对应模块的 _规格原文/（不删除、不修改原文件）

② 冗余审计
   python 工具/提取目录.py  →  看有多少节
   通读一遍，列出重复项（本项目实测：输出模板重复 6 处、调整指令 7 处、执行流程 2 处…）

③ 提炼
   写成「引擎文件」（声明式、无冗余、可直接部署）
   原则：保留全部可复用词汇与机制，只删重复表述与冗余指令

④ 保真度验证  ← 关键步骤，不可省
   写脚本对比原文与提炼版的关键词汇清单
   标准：原文命中的关键词，提炼版 0 丢失
   （这一步是「提炼」与「阉割」的分界）

⑤ 建落点索引
   在 _规格原文/README.md 里把每节映射到提炼版章节
   并明确标注「只在原文里的内容」+ 何时该查原文

⑥ 接线（最易漏，见下）
   主控指向新引擎 · 模块 README · INDEX · 根 README · 部署指南 · 总控路由

⑦ 校验
   python 工具/校验.py  →  6 项全过
   另：把新机制加进 MECHANISM_RULES，防止未来漏同步
```

## 四、改动后的三层同步（第 ⑥ 步的展开）

接线时最容易只改上两层而漏掉实体层：

| 层 | 内容 | 必须同步 |
|---|---|---|
| ① 事实来源层 | 规格原文 · 各模块 `00-主控智能体.md` | — |
| ② 规则层 | `引擎/*.md` · 模块 `README.md` | 指向 ① 的引用 |
| ③ **实体层** | `模板/*` · 可部署合并版/总集 · `项目骨架/` 下 `_README` | ⚠️ **逐个同步** |

**优先检查会被用户直接复制的文件**（模板、合并版），它们比 README 更重要。

## 五、局限（诚实说明）

1. **机制覆盖是"关键词存在性"检查**，不是语义检查。若有人在文件里写"本模块**没有** ID 注册表机制"，关键词存在即通过。**它抓的是"漏改"，不是"改错"。**
2. **口径一致依赖人工维护词表**——新增数字口径时需手动加一条 `STALE_TERMS` 规则。
3. **不能替代实际跑一遍示例**——本项目的经验是「结构完备性不能靠通读文档判断，必须实际跑一个完整示例」（见 `示例演示/01-全流程走通.md`）。本工具只覆盖**机械一致性**，覆盖不了**逻辑可用性**。
